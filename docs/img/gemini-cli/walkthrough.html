Add Gemini CLI as a first-class ACP harness

Gemini CLI is a shipped New Chat / Settings card. JaBot talks to the vendor binary over documented ACP — gemini --acp — not a wrapper package.

How it works

Claude, Codex, and Pi each have an ACP adapter on PATH. Gemini does not: the CLI is the adapter. Official docs (updated 2026-04-10) start that mode with gemini --acp. Older builds only advertised --experimental-acp.

Catalog card → Doctor inspect → snapshot the flag --help lists → ACP session in the thread worktree

Doctor answers four questions from the same binary: is gemini installed, does this build speak ACP, is anyone signed in (env / ~/.gemini profile / Vertex ADC), and is the selected model/project usable. Missing install, outdated flags, logged-out, and empty model.name each get a status plus a remedy — never a silent ready.

An empty end_turn is empty_response, same as #203. Cancel, streaming, tools, and permission asks ride the existing ACP client. Gemini advertises session/load, not resume or close; the supervisor already falls back.

Auth and isolation

Gemini owns one OS-user profile under ~/.gemini. JaBot’s Google MCP grant (Gmail / Calendar / Drive) is a different OAuth client and is not copied across. Every Gemini thread on the machine shares that profile. ACP authenticate can persist security.auth.selectedType.

Onboarding can pin @google/gemini-cli@0.58.0 into ~/.local. Sign-in stays separate: run gemini once, or export GEMINI_API_KEY.
