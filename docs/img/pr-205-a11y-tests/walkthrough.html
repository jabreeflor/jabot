JaBot · PR #205 walkthrough

Add automated accessibility tests for primary views

Axe-core now runs inside the existing Vitest unit project. A new critical or serious violation on the sidebar, chat thread, Settings, PR board, or New Chat / harness picker fails the same gate CI already runs.

How it works

Before

  • Views had role and label tests, but no axe scan.
  • A nameless control could land on main if nobody wrote a getByRole assertion for it.
  • Nothing in CI failed on a new serious violation.
→

After

  • Each primary view renders with the fixtures the unit tests already trust.
  • axe.run scores the DOM; only critical/serious findings throw.
  • verify.sh already runs the unit project, so CI picks this up for free.

Fails the run Critical and serious WCAG 2.0/2.1 A/AA findings. The helper’s first test is a nameless button, so a silent no-op cannot pass.

The one product fix the gate required: an open Select listbox had no accessible name. It is now labelled from its trigger via aria-labelledby, and the trigger points at the list with aria-controls.

How to verify

  • Run npm run test:a11y — six tests, including the nameless-button failure and the five views.
  • Open the harness picker in that suite and confirm the listbox is named from Harness: ….
  • ./scripts/verify.sh already includes them via npx vitest run --project unit. This PR’s push ran that gate green.
  • To add a view later: render it the way its unit test does, then call expectNoSeriousA11yViolations(container).
