Windows window chrome without macOS private API

A usable Win10/11 window that does not use an overlay title bar or under-window vibrancy. The cargo feature stays for tauri-build's allowlist; Windows never calls the API. Closes #282. Parent tracking issue #280.

How it works

1. Shared config is a decorated opaque window tauri.conf.json holds size, title, and macOSPrivateApi: true (the allowlist pair — see step 2). Overlay, transparency, and underWindowBackground live only in tauri.macos.conf.json. Windows inherits the shared window; tauri.windows.conf.json is left for #291 (NSIS), not chrome.
2. Private API is unused off macOS macOSPrivateApi stays in the shared config and macos-private-api stays on the untargeted tauri dep: tauri-build's allowlist is bidirectional. Windows/Linux never call the API — window.rs returns before clearing the fill, and the Windows window is decorated and opaque.
3. Host reports the frame it drew window_chrome returns overlay or decorated (cfg!, same pattern as translucency). apply() returns before clearing the webview fill off macOS, so a decorated window cannot show the desktop through a hole.
4. Renderer drops overlay insets data-window-chrome="decorated" zeros --titlebar-h / --traffic-lights-w, hides the drag strip, and sets --collapsed-rail-w to 56px (toggle-wide). Chat and agent pills sit flush under the OS title bar. live.sh uses ?chrome=decorated / overlay to shoot both frames on Linux.
5. Close exits on Windows macOS still hides to Dock (#4). Windows / Linux: the title-bar close button exits. No system tray, no hide-to-tray. Minimize keeps the process. Glass stays solid when vibrancy is unsupported (#278). Mica/Acrylic is out of scope.

How to verify
