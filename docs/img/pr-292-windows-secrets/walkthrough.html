Windows secrets via Credential Manager (#283)

Same host put / get / delete on macOS and Windows. Bytes stay in the OS store; SQLite keeps pointers only. Linux still fails closed. Parent: #280.

How it works

1. One vault type, two OS backends Secrets::platform() returns Os on macOS and Windows. Call sites are unguarded: pairing, tool OAuth, and Store::put_secret all go through the same methods.
2. keyring 3, feature-split by target macOS keeps apple-native (Keychain generic password, service com.jabot.app). Windows adds windows-native (Credential Manager generic credential, target {account}.{service}). Linux never downloads either crate.
3. hello reports where bytes live store.secretsBackend is keychain, credential-manager, memory, or unavailable. Acceptance isolation still uses JABOT_KEYCHAIN_SERVICE=com.jabot.app.acceptance.*.
4. Denied access is explicit keyring::Error::NoStorageAccess and Windows/macOS “access denied” phrases become StoreError::SecretsDenied, logged as secrets: credential store denied access (account): … with no secret bytes. Pairing and tool RPC already surface {err}.

Where secret bytes live

macOS
Keychain Access → login keychain → service com.jabot.app
Windows
Credential Manager → Windows Credentials → {account}.com.jabot.app
Linux / CI
No OS store. put is SecretsUnavailable unless JABOT_SECRETS_BACKEND=memory
